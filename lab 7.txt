Lab 7: Patient Record Lookup (Dictionaries)

20 points. Due Sunday 11:55pm.
Scenario

Lab 6 stored each patient as a tuple: fields identified by position. That works until a record has a field that's sometimes missing, then position-based tuples get fragile. This lab stores each patient as a dictionary, where fields are identified by name instead of position, and introduces .get() to handle a field that isn't always present.

This is the same five-patient roster as Lab 6, with the same weight and height values, so your BMI numbers should match what you calculated in Lab 6. The difference this week is the data structure and two new patient-record fields: patient_id and condition. Not every patient has a condition on file.

Requirements

    Use .get() with a default value for the condition field. Do not use square-bracket access (patient["condition"]) for that field, it will crash on P002 and P005.
    Use .title() (or equivalent string formatting) to capitalize names and conditions for display. Don't retype the data in capitalized form, the stored data stays lowercase.
    find_patient_by_id() must be a real function with a docstring, not inlined logic copy-pasted at the lookup step.
    Your BMI numbers must match Lab 6's for the same patients. If they don't, you have a bug in the formula, not a different valid answer.

Watch Out For

    .get("condition", "Not specified") returns the default only when the key is completely missing. A patient with "condition": "" would get the empty string back, not the default. That's not a case in this dataset, but know the difference.
    .title() capitalizes every word, including after a comma: "alvarez, maria".title() gives "Alvarez, Maria", which is what you want here, but .title() can behave oddly on text with apostrophes or hyphens. Not an issue with this dataset, worth knowing for later.
    Returning None from find_patient_by_id() when nothing matches is required, not optional, later labs build on functions failing gracefully instead of crashing.
